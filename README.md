# متجر تيشيرتات مطبوعة — الهيرو ثلاثي الأبعاد

PHP خام بلا إطار عمل، وواجهة بلا خطوة بناء، ولا مورد واحد من CDN خارجي.
مصمَّم ليعمل كاملًا على استضافة مشتركة بلا وصول إلى سطر الأوامر، وليصبح
الانتقال إلى VPS **تغيير سطر في ملف تهيئة** لا إعادة كتابة.

---

## التشغيل

يتطلّب PHP 8.2 فأعلى و MySQL 5.7 / MariaDB 10.2 فأعلى. الامتدادات المستخدمة
(`pdo_mysql`, `gd`, `fileinfo`, `dom`, `zip`, `openssl`) موجودة افتراضيًا على كل
استضافة تقريبًا. `zip` لتصدير أوامر الإنتاج، و`openssl` لبريد SMTP.

```bash
composer install --no-dev          # FPDF و PHPMailer، ولا شيء غيرهما
mysql -u root -e "CREATE DATABASE tshirt_store CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
mysql -u root tshirt_store < schema.sql
cp config/local.example.php config/local.php   # ثم املأه
php tools/make-images.php --seed               # صور البذور بمقاساتها
```

> **`schema.sql` يُسقِط الجداول ويعيد إنشاءها.** هو مخطط التنصيب لا ترحيلًا؛ لا
> تُشغِّله على قاعدة فيها طلبات.

`config/local.php` يُدمج مفتاحًا بمفتاح فوق ملفات `config/`، فلا تكتب فيه إلا ما
يختلف. هو الطريق الأساسي لأن **متغيّرات البيئة غير موثوقة**: كثير من الاستضافات
المشتركة لا تتيح ضبطها أصلًا، و`variables_order` في PHP كثيرًا ما يُسقط `E`
فيعود `getenv()` فارغًا حتى لو ضبطتها الصدفة. الملف يعمل دائمًا.

إن أتاح مستضيفك متغيّرات بيئة حقيقية، احذف الملف واستخدمها — التهيئة تقرأ
`$_SERVER` و`$_ENV` و`getenv()` بهذا الترتيب:
`DB_HOST` `DB_PORT` `DB_NAME` `DB_USER` `DB_PASS` `ADMIN_USER` `ADMIN_HASH`
`CRON_KEY` `PRINT_DRIVER` `PAYMENT_DRIVER` `APP_URL` `APP_DEBUG`
`MAIL_DRIVER` `MAIL_HOST` `MAIL_PORT` `MAIL_ENCRYPTION` `MAIL_USERNAME`
`MAIL_PASSWORD` `MAIL_FROM` `MAIL_FROM_NAME` `MAIL_BCC`.

‏`MAIL_DRIVER` يبدأ على `log` — يكتب الرسالة في `storage/logs/mail` ولا يرسل.
اضبطه على `smtp` مع بيانات صندوق النطاق قبل الإطلاق.

توليد كلمة مرور الآدمن:

```bash
php -r 'echo password_hash("كلمة-مرورك", PASSWORD_DEFAULT), PHP_EOL;'
```

الدخول على `/admin/`. للتجربة محليًا: `php -S 127.0.0.1:8899 -t public`، أو مع
موجّه الضغط `php -S 127.0.0.1:8899 -t public tools/router.php` إن كنت ستقيس زمنًا
(الخادم المدمج لا يقرأ `.htaccess`).

### الهيرو فارغ؟

البطاقة الداكنة تقول لك السبب بدل أن تصمت. الأسباب الثلاثة، بالترتيب:

1. **لا قاعدة بيانات** — أنشئها وحمّل `schema.sql` كما أعلاه.
2. **بيانات اتصال خاطئة** — فعّل `'debug' => true` في `config/local.php` فتظهر
   رسالة PDO نفسها داخل البطاقة، وتُسجَّل دائمًا في `storage/logs/php.log`.
3. **لا شريحة نشطة** — الجدول موجود لكنه فارغ أو كل الشرائح معطّلة. شغّل البذور
   أو فعّل شريحة من `/admin/`.

الكاش في `storage/cache/hero.slides.json` عمره ساعة ويُبطَل عند أي حفظ؛ احذفه
يدويًا إن غيّرت الصفوف من خارج لوحة التحكم.

### جذر الويب

اجعل جذر الويب `public/`. يبقى `src/` و `config/` و `storage/` و `vendor/`
خارجه، ويصبح `/admin/` قابلًا للوصول لأنه داخل `public/`. ملف `.htaccess` في
الجذر يحوّل الطلبات إلى `public/` ويمنع الوصول إلى ما عداه، لو تعذّر ضبط الجذر
على المستضيف.

### الطابور

على الاستضافة المشتركة: استدعِ `https://example.com/cron.php?key=…` كل دقيقة من
Cron لوحة الاستضافة. على VPS: `php public/cron.php --loop` تحت systemd. **الخدمات
لا تتغيّر بين الحالتين** — الفرق كله في نقطة الاستدعاء.

## الفصل المعماري

منطق الأعمال في `src/Service/` يستقبل مصفوفات ويُعيد مصفوفات أو يرمي
استثناءات. لا يعرف `$_POST` ولا `echo` ولا وسمًا واحدًا. فوقه طبقتان رقيقتان
تستدعيان **الخدمة نفسها**:

- `public/*.php` — تصيّر HTML
- `public/api/*.php` — تعيد JSON

هذا ما سيتحدّث إليه محرّر التصميم بـ React لاحقًا، وما سيتحدّث إليه تطبيق جوال
إن وُجد. القاعدة مفروضة آليًا لا بالمراجعة:

```bash
php tools/audit-layers.php
```

يُحلّل الملفات بـ `token_get_all` ويرفض أي `echo` أو HTML مضمّن أو متغيّر عام
داخل `Service` أو `Repository` أو `Print`.

```
config/          app.php  db.php  garments.php  print.php
src/
  Service/       HeroSlide · Product · Cart · Order · PrintFile · Design
  Print/         PrintDriverInterface + Imagick · Shell · Passthrough + Factory
  Repository/    وصول PDO فقط، كل استعلام مُجهَّز
  Support/       Db Auth Csrf Cache Validator Uploader Response Queue RateLimiter Garment
  View/          قوالب مشتركة — hero.php يستخدمه الموقع والمحرّر معًا
public/
  index.php  catalog.php  product.php  cart.php  checkout.php  cron.php
  api/       cart.php  design.php  upload.php
  admin/     index · edit · save · upload · orders · download · system · login · logout
  assets/    css · js · js/vendor/three · fonts · editor (ناتج بناء الجزيرة)
editor-src/  مشروع Vite مستقل — محرّر التصميم بـ React
storage/     cache · print · logs · originals · print/designs   (خارج جذر الويب)
tools/       أدوات مطوّر لمرّة واحدة + حزم الفحص
```

## الهيرو

خمس طبقات مكدّسة داخل بطاقة داكنة بانحناء ‎46px‎، والتنقّل خارجها فوقها:

| الطبقة | z |
|---|---|
| العناصر الأمامية (السطر التسويقي + بطاقتا الإحصاء) | 40 |
| كانفس WebGL — خلفية شفافة | 30 |
| اللسان الفاتح | 22 |
| الكلمة العملاقة | 20 |
| خلفية البطاقة | 10 |

النصوص كلها DOM حقيقي؛ لا شيء منها يُرسم داخل مشهد three.js.

**اللسان بين الكلمة والقميص، لا فوقهما.** مرور القميص أمامه هو مصدر الإحساس
بالعمق في التصميم كله؛ فوق الكانفس يصير بطاقة ملصقة على صورة مسطّحة. الرقم وحده
لا يكفي: `clip-path` على `.hero__surface` ينشئ سياق تكديس، فكل ما بداخلها يُرسم
ككتلة واحدة مهما كانت أرقامها، وقصّة اللسان ثقب في السطح فما رُسم داخله لا يصل
إليه أصلًا. لذلك لم يبقَ داخل `.hero__surface` سوى الخلفية والكلمة العملاقة،
وانتقل المسرح والطبقة الأمامية والواجهة إلى مستوى البطاقة إخوةً لها.

يُفحص هذا بالبكسل لا بقراءة الرقم: `verify-hero` يركن اللسان في منتصف البطاقة
عبر `--dx`/`--dy` نفسها التي يكتبها المحرّر، يصوّر البطاقة أربع مرات — كاملة،
بلا لسان، بلا مسرح، وبلا الاثنين — ويسأل: هل بقي للسان بكسل واحد بعد رسم القميص؟
عند `z-22` الجواب صفر من ٨١٢ على سطح المكتب و٠ من ١٤٥٣ على الجوال؛ عند `z-60`
ينقلب الرقمان إلى ١٠٠٪.

**الزاوية المقعّرة** جزء من مسار قص واحد على سطح المشهد كاملًا عبر
`clip-path: shape()`، وليست عنصرًا فاتحًا ملتصقًا بخلفية داكنة. لذلك لا توجد
حافتان تتراكبان أو وصلة تُظهر بكسلات داكنة عند التكبير. يتبدّل المسار تلقائيًا
مع اتجاه الصفحة، وتبقى لوحة مستديرة عادية في المتصفحات التي لا تدعم `shape()`.

**الأداء**: اللقطة الثابتة تُعرض فورًا بـ `fetchpriority="high"`، وthree.js لا
تُحمَّل إلا بعد حدث `load` عبر `import()`، ثم تلاشٍ ٤٠٠ مللي ثانية. سياق
`WebGLRenderer` واحد لكل الشرائح؛ التبديل يغيّر اللون والخامة فقط. حلقة الرسم
تتوقّف بـ `IntersectionObserver` خارج العرض، ولا تقيس التخطيط داخل الإطار.

**الإزاحات** عبر عرض البطاقة كاملًا، بتنعيم `lerp` بمعامل 0.075:
الخلفية ٢٪، الكلمة ٥٪، العناصر الأمامية ٨٪، والموديل ±٦ درجات. اللسان لا يتأثر
بحركة المؤشر حتى يبقى متصلًا بحافة البطاقة.

**الجوال**: على `pointer: coarse` أو عرض أقل من ٧٦٨ بكسل لا يُطلب أي ملف من
`vendor/three` ولا الموديل. `prefers-reduced-motion` يوقف الحركة والتبديل.

**المقاسات** بوحدات الحاوية (`cqw` / `cqh`) لا النافذة، فتظهر المعاينة داخل
لوحة التحكم بالمقاس الذي سيراه الزائر رغم أن اللوحة أضيق من الشاشة.

ولا ثابت تخطيط مكرّر بين الاثنين. المعاينة كانت تنحرف ٥٫٤٪ عمّا يراه الزائر لأن
ارتفاع الشريط العلوي كُتب مرتين — مرة كارتفاع، ومرة كـ `--hero-surface-top` —
وكانت الثانية وحدها خلف `.has-hero`، وهو صنف لا تحمله صفحة اللوحة. صار الرقم
إعلانًا واحدًا في `:root` يقرأه الشريط والسطح معًا، فسقط الانحراف إلى ٠٫٢٪ عند
عتبة ١٪. و`admin.css` ممنوع من إعادة ذكر أي مقاس صندوق للهيرو — يفحص
`verify-admin` ورقة الأنماط نصًّا، لأن التكرار هو ما يعود لا الرقم.

`hero.js` و `hero3d.js` ملفان لا ملف واحد: الاستيراد الديناميكي لا يجزّئ ملفًا،
والفصل هو ما يمنع وصول three.js إلى الجوال.

## طبقة الطباعة

`PrintFileService` لا تعرف كيف تُعالَج الصور. كل ما يحتاج امتدادًا أو ثنائيًا
يمرّ عبر `PrintDriverInterface`:

| السائق | متى | كيف |
|---|---|---|
| `ImagickDriver` | امتداد `imagick` محمّل | مكتبة مرتبطة، **بلا `exec`** |
| `ShellDriver` | VPS | `proc_open` إلى ImageMagick |
| `PassthroughDriver` | لا هذا ولا ذاك | PNG بدقّة ٣٠٠ في RGB، والتحويل عند المطبعة |

الاختيار تلقائي عبر `isAvailable()` مع إمكانية الإجبار من `config/print.php`.
هندسة الصفحة (علامات القص، هامش الأمان، الأبعاد الفيزيائية) واحدة في السائقات
الثلاثة عبر `AbstractPrintDriver` وFPDF — PHP خالص — فيصل المطبعةَ الملفُّ نفسه
شكلًا من أي بيئة. الفرق بين السائقات حيث يمكن أن يكون فرقًا حقيقيًا: الفضاء
اللوني، وهو مُسجَّل في `print_files.colour_space` مع اسم السائق.

**فحص الدقّة** يسبق البيع ويجري بـ `getimagesize` وحدها — دالة أساسية لا تحتاج
أي امتداد. أقل من ١٥٠ DPI عند ٢٨×٣٥ سم تحذير، وأقل من ١٠٠ رفض. التصميم المتجهي
بلا سقف دقّة.

المخرجات في `storage/print/` خارج `public`، وتُقدَّم عبر `admin/download.php`
بعد فحص الجلسة وبـ `realpath` يمنع الخروج من المجلد.

## تصحيحان على الثوابت المُسلَّمة

ثوابت `config/garments.php` مقيسة من الشبكة نفسها بـ
`tools/measure-print-area.mjs`، وتختلف عمّا ورد في المواصفة لأن المواصفة لا
تطابق هذا الموديل. الفرق مُثبت بالعرض:

**١. منطقة الطباعة تضع التصميم على الأكمام.** المستطيل المذكور
(`v0=0.111, v1=0.395`، أي `y=1239` على كانفس ٢٠٤٨) يقع خارج لوح الصدر تمامًا.
الصدر عند `v` بين ‎0.26‎ و‎0.55‎، والمستطيل الصحيح `x=241, y=920, w=505, h=596`.

**٢. التباين الاتجاهي ٠٫٨٪ لا ١٩٪.** قياس `|dP/du|` و`|dP/dv|` على ٧٣٣ مثلثًا
في الصدر يعطي `u = 124.5` و`v = 123.5`. قيمة `v` في المواصفة صحيحة تقريبًا؛
`u = 103.9` هي الخاطئة وهي مصدر الـ ١٩٪.

صيغة المستطيل الواردة (`y = (1 - v1) × S`) **صحيحة** — `v` يزداد صعودًا على
القميص — بشرط ترك `flipY` على قيمته الافتراضية في `CanvasTexture`. الرسم يمرّ
عبر `drawImage` إلى المستطيل بالبكسل بعد ملاءمة التصميم بالسنتيمتر، فيخرج
المربّع مربّعًا أيًّا كان التباين.

> أضفت عمودًا واحدًا لم يرد في المخطط المُسلَّم: `hero_slides.layout` (‏TEXT
> اختياري). المخطط لا يحوي أعمدة موضع، ومقابض السحب المطلوبة في المهمة ٣ لا
> يمكن أن تحفظ شيئًا بدونه. العمود يخزّن **إزاحة** عن موضع الـ CSS لا موضعًا
> مطلقًا، فشريحة لم تُسحب قط تُخزَّن `NULL` وتبقى الأنماط هي المرجع.

## أدوات المطوّر

تُشغَّل على جهاز المطوّر لا على الخادم. الخادم لا يحتاج Node إطلاقًا.

```bash
npm i -D @gltf-transform/core @gltf-transform/extensions \
         @gltf-transform/functions sharp puppeteer-core

node tools/prepare-model.mjs basic_t-shirt.glb public/models/tshirt.glb
node tools/measure-print-area.mjs        # يطبع كتلة config/garments.php
node tools/render-poster.mjs             # public/images/hero-poster.webp
php  tools/make-images.php --seed        # صور المنتجات والتصاميم بمقاساتها الثلاثة
php  tools/make-images.php <ملف>          # المقاسات الثلاثة لصورة بعينها
```

### حزم الفحص

```bash
php  tools/audit-layers.php              # المعيار ١٢
php  tools/verify-backend.php            # المعايير ٦ ٧ ٨ ٩ ١٠ ١١ + تعقيم SVG
php  tools/verify-orders.php             # الطلب والطابور وملف الطباعة
node tools/verify-hero.mjs               # المعايير ١ ٢ ٣ ٤ ٥ ١٣ + الوصولية
ADMIN_PASSWORD=… node tools/verify-admin.mjs
node tools/verify-uv.mjs                 # إلزامي قبل أي عمل على المحرّر
node tools/verify-editor.mjs             # معايير المحرّر + زمن الوصول إلى التفاعل
php  tools/verify-store.php              # معايير المتجر الاثنا عشر
```

`render-poster` و `measure-print-area` و `verify-*` تحتاج الموقع مخدومًا على
`127.0.0.1:8899` وChrome مثبّتًا. `verify-editor` وحده يحتاج الموجّه معه —
`php -S 127.0.0.1:8899 -t public tools/router.php` — لأنه يقيس زمنًا، والخادم
المدمج بلا الموجّه يرسل الجزيرة بلا ضغط. اللقطة تُرسم من `hero3d.js` نفسه، فتؤطّر
القميص كما يؤطّره المشهد ولا يتحرّك شيء أثناء التلاشي.

## تجهيز الموديل

`tools/prepare-model.mjs` خطوة يدوية لمرّة واحدة، وأي موديل جديد يمرّ بها:

1. `KHR_materials_pbrSpecularGlossiness` مهجور وغير مدعوم في three.js الحديثة،
   فيُحوَّل إلى metallic-roughness.
2. التحويل يخلّف امتدادَي specular/ior بنسيجين مصمتين يفرضان
   `MeshPhysicalMaterial`؛ يُحذفان.
3. نسيج الـ diffuse صورة ١٠٢٤×١٠٢٤ بلون واحد (‏`#47423B` مقيسًا، تباين ±١ بلا
   إضاءة مخبوزة)، ونسيج الـ metallic-roughness مصمت أيضًا. كلاهما يصير معاملًا
   عدديًا، ويبقى `baseColorFactor` أبيض ليعمل التلوين عبر `material.color`.
4. خريطة الـ normal تبقى وتُضغط webp، و `doubleSided: true` كما هو.
5. `asset.extras` — وفيه الإسناد — لا يُمَسّ.

بلا ضغط هندسي: Draco وMeshopt يحتاجان فاكّ تشفير يُشحن بجوار three.js، ولا
خطوة بناء هنا. النتيجة **٣٣٠ كيلوبايت** من أصل ١٫٣ ميغابايت.

## محرّر التصميم — جزيرة React

الموقع كلّه PHP يصيّر HTML وJavaScript خام. **المحرّر وحده** جزيرة React، لأن
حالته — طبقات، تحديد، تراجع/إعادة، تزامن كانفس ثنائي الأبعاد مع موديل ثلاثي —
تتحوّل بسرعة إلى كود صعب الصيانة بلا إطار.

### الحدّ

React لا يظهر في أي صفحة أخرى. صفحة المنتج تشحن **مُشغِّلًا من ١٫٨ كيلوبايت**
بلا إطار، يستدعي `import()` عند الضغط على «صمّم بنفسك» ويحقن ورقة الأنماط حينها.
قبل الضغط: **صفر بايت** من الحزمة — مقيس في تبويب الشبكة لا مفترضًا.

المُشغِّل — `public/assets/js/editor-launch.js` — هو ما يُدرَج في صفحة المنتج،
لا `<script type="module" src="/assets/editor/editor.js">`. وسم `src` كان يُنزّل
الحزمة لكل زائر جاء ينظر إلى قميص، وهو ما يناقض «صفر بايت قبل الضغط». اعتُمد هذا
الانحراف عن نص المواصفة الأول، وهذا الملف يصف ما هو مبنيّ فعلًا.

المُشغِّل يتولّى أيضًا حالة التحميل: يُظهر `#editor-loading` عند الضغط ولا يخفيه
حتى تُطلق الجزيرة الحدث `tshirt-editor:ready`. لحظة وصول الحزمة أبكر من لحظة
جاهزية المحرّر بنصف ثانية تقريبًا، وتلك الفجوة هي بالضبط ما كانت حالة التحميل
موجودة لتغطيته.

### البناء

```bash
cd editor-src
npm install
npm run build     # -> public/assets/editor/  (editor.js + editor-scene.js + editor.css)
npm run size      # يطبع الأحجام للتتبّع — لا يفشل ولا يوقف البناء
```

البناء على جهاز المطوّر فقط. الخادم يستقبل ملفات ثابتة ولا يحتاج Node.

‏`editor.js` هو المدخل الوحيد الذي تسمّيه PHP؛ يسحب `editor-scene.js` خلفه
باستيراد نسبيّ يحلّه المتصفح وحده. النشر كما كان: انسخ المجلد.

### الفكرة الجوهرية

لا شيء يُرسم على الموديل. كانفس Fabric بمقاس مساحة الطباعة يُنسخ بـ `drawImage`
إلى أطلس ‏٢٠٤٨×٢٠٤٨ عند مستطيل الوجه الحالي، والأطلس هو ما يعاينه three.js عبر
`CanvasTexture`. الأمام والخلف يتشاركان الأطلس نفسه لأن الموديل يستخدم تخطيط UV
واحدًا: لا materials متعددة ولا decals.

القصّ ليس قاعدة يمكن نسيانها: الكانفس **هو** مساحة الطباعة، فما يخرج عنه لا
يُرسم أصلًا، ومع ذلك يوجد `clipPath` احتياطي لأن الظل أو الحدّ قد يتسرّب بكسلًا.

### الهندسة — مصدر واحد

كل رقم يأتي من `config/garments.php` عبر `App\Support\Garment`، ويصل الجزيرة في
كتلة `editor-config`. لا رقم هندسي واحد مكتوب في كود React، ولا في PHP خارج
`Garment`. مقاس كانفس العمل نفسه (‏١٠٠٠×١٢٥٠) يشتقّه `Garment::workPx()` لا
الجزيرة، حتى لا تنحرف اللغتان.

`Garment` يشتقّ أيضًا ما لم يكن في المواصفة: **مساحة التصميم القابلة للبيع**.
لوح UV المقيس يغطّي ‎30.68×35.91‎ سم لأن صندوقًا محيطًا بعيّنة رؤوس يتجاوزها
دائمًا، بينما العميل يشتري ‎٢٨×٣٥‎ والتصدير يجب أن يكون ‎٢٨×٣٥‎ عند ٣٠٠ DPI
بالضبط. المستطيل المتمركز `design_rect_px` هو الاثنان معًا.

### التباين الاتجاهي — مقيس لا مفترض

`tools/verify-uv.mjs` يسبق أي عمل على المحرّر ويقيس مرّتين:

1. **على الشبكة الهندسية** — ‏`|dP/du|` و`|dP/dv|` على ٥٨٣ مثلثًا داخل مستطيل
   التصميم: ‏١٢٤٫٥٨ مقابل ‏١٢٣٫٣٤ سم للوحدة، أي **‎-0.99٪‎**. لا معامل تعويض في
   أي مكان من الكود.
2. **على العرض** — شبكة ‏٣٫٥ سم تظهر خلاياها مربّعة (‎-1.03٪‎)، والمستطيل المطبوع
   يُعرَض بنسبته الحقيقية (‎0.800‎ متوقّعة، ‎0.803‎ مقيسة).

مربّع وقرص بنفس المقاس يقيسان **نفس النسبة بالضبط** (‏1.0611): الفارق الباقي
إسقاط منظور — وسط الصدر أقرب إلى العدسة من طرفيه، تمامًا كما في صورة فوتوغرافية
لقميص مطبوع.

### المخرجات

`POST` واحد إلى `/api/design.php` يحمل `design_json` و`print_png` و`preview_png`
والوجه والكمية والرمز. الخادم:

- يرفض أي `print_png` ليس بمقاس التصدير المضبوط.
- **يعيد حساب الدقّة بنفسه** من أبعاد الأصل المحفوظة في `design_json` مقابل
  المساحة التي يغطّيها العنصر — لا يصدّق رقم المتصفح.
- يحفظ نسخة الطباعة في `storage/print/designs/` خارج جذر الويب، والمعاينة وحدها
  تحت `public`.

ثم تُضاف السلعة بطلب نموذج عادي إلى `/cart.php`، والسعر يُقرأ من الكتالوج:
لا حقل سعر في أي من الطلبين.

### زمن الوصول إلى التفاعل

المعيار زمن، لا بايتات: **من الضغط على «صمّم بنفسك» إلى إمكانية الرسم، أقل من
٢٫٥ ثانية على 4G مخنوق، وحالة تحميل مرئية طوال المدة.**

المقيس: **١٣٣٤ ملّي ثانية**. الظرف — ‏1.6 ميغابت/ث نزولًا، ١٥٠ ملّي ثانية تأخيرًا
(‏Slow 4G في Chrome)، ذاكرة تخزين مؤقت باردة. تُقاس في القسم ٩ من
`tools/verify-editor.mjs`، والساعة تتوقّف عند اللحظة التي يقبل فيها كانفس التصميم
سحبًا — لا عند وصول آخر بايت من الحزمة، وبينهما نحو نصف ثانية.

ثلاثة أشياء صنعت الفرق، بالترتيب:

| | قبل | بعد |
|---|---|---|
| بلا ضغط، حزمة واحدة | ٨٢٥٣ م.ث | |
| ‏`mod_deflate` في `.htaccess` (‏١٢٧٧ ← ٣٦٢ ك.ب) | | ٢٧٩١ م.ث |
| فصل three.js عن المسار الحرج | | **١٣٣٤ م.ث** |

الفصل هو الجوهري. ‏three.js يزن ١٨٦ كيلوبايت مضغوطة من أصل ٣٦٢، ولا سطر منه
لازم لوضع تصميم على القميص — إنما لعرض القميص. فصار `Preview.jsx` خلف
`React.lazy`: يفتح المحرّر على ١٣٨ كيلوبايت، ويصل المشهد بعده بلحظة وراء
`Suspense` يقول ما ينتظره. لا يمكن بلوغ ٢٫٥ ثانية بهذا المكدّس دون هذا الفصل:
‏٣٦٢ كيلوبايت على ١٫٦ ميغابت/ث تستغرق ٢٫٤ ثانية نقلًا وحده.

الأحجام بقيت للتتبّع لا للحكم:

| | مضغوطة |
|---|---|
| ‏`editor.js` — react + fabric + كود المحرّر | ١٣٦ ك.ب |
| ‏`editor.css` | ١٫٧ |
| **قبل أول ضربة فرشاة** | **١٣٨** |
| ‏`editor-scene.js` — three + r3f، بعد الفتح | ٢٢٥ |
| المجموع | ٣٦٣ |

`npm run size` يطبع هذا الجدول في كل بناء ولا يفشل أبدًا. المعيار القديم — ٣٠٠
كيلوبايت مضغوطة — كان غير قابل للتحقيق بهذا المكدّس أصلًا: ‏three وfabric
وreact-dom وr3f وحدها ٣٦١ كيلوبايت قبل سطر واحد من كود المحرّر، و`@react-three/fiber`
يستورد three بعرضه فيُبطل التقليم الشجري (الاستيرادات المسمّاة وفّرت ٣ كيلوبايت،
وحذف بيئة الإضاءة ٠٫٩). الحجم كان بديلًا سيئًا عمّا يهمّ فعلًا وهو الانتظار،
والانتظار يُعالَج بالتحميل المتأخّر والضغط والتقسيم — لا بتغيير المكدّس.

### الضغط

`public/.htaccess` يفعّل `mod_deflate` و`mod_brotli` للنصوص. خادم PHP المدمج
لا يقرأ `.htaccess`، فقياس الزمن محليًا يحتاج الموجّه:

```bash
php -S 127.0.0.1:8899 -t public tools/router.php
```

الموجّه يطبّق الضغط الذي يعلنه `.htaccess` ولا شيء غيره، ويقع خارج جذر الويب فلا
يُطلب كعنوان ولا يعمل في الإنتاج. بدونه القياس يقيس الأداة لا الموقع، ولذلك
يفحص القسم ٩ الترميز على السلك ويقول ذلك صراحة عند الإخفاق.

### الفحص

```bash
node tools/verify-uv.mjs        # إلزامي، يسبق كل شيء
node tools/verify-editor.mjs    # المعايير العشرة
```

## المتجر — الكتالوج والسلة والطلبات

### نموذج البيانات

الفكرة المحورية: **القميص الخام منتج، والتصميم الجاهز شيء يُطبع عليه، وتصميم
العميل شيء ثالث.**

| الجدول | ما فيه |
|---|---|
| `products` | القميص الخام: القماش، القصّة، العناية. لا لون ولا مقاس ولا سعر |
| `product_variants` | لون × مقاس ← `sku`, `price_cents`, `stock` |
| `colors` `sizes` | مراجع. المقاس يحمل عرض الصدر والطول بالسنتيمتر |
| `designs` | تصميم جاهز من الكتالوج: سعر إضافي، بلا مخزون |
| `design_products` | أي تصميم متاح على أي قميص |
| `custom_designs` | تصميم العميل — من المحرّر أو من الرفع المباشر |
| `carts` `cart_items` | السلة صفوف لا جلسة |
| `orders` `order_items` | الطلب، بكل ما تحتاجه أرضية الإنتاج منسوخًا فيه |
| `customers` `addresses` | حساب اختياري |

**لماذا التصميم ليس منتجًا:** لو كان كل تصميم منتجًا لتضاعف جدول المتغيّرات
بحجم كتالوج التصاميم — عشرون تصميمًا × ستة ألوان × خمسة مقاسات = ٦٠٠ صفًا لشيء
واحد مخزونه صفر أصلًا. **المخزون على `product_variants` وحده**، لأن ما ينفد هو
القميص لا الرسم؛ والتصاميم تُطبع عند الطلب.

`cart_items` و`order_items` يحملان أحد ثلاثة أشكال عبر `item_type`:
‏`blank` بلا طباعة، `ready` بـ `design_id`، `custom` بـ `custom_design_id`.
‏MariaDB 10.2 يقرأ قيود `CHECK` ويتجاهلها، فالقاعدة مفروضة في `CartService`
ويؤكّدها الفحص — لا مُسلَّمة للمخطط.

**سطور الطلب منسوخة لا موصولة.** اسم المنتج واللون والمقاس والسعر تُكتب في
`order_items` وقت الطلب. تغيير اسم لون في آذار يجب ألا يغيّر ما يقوله طلب من
كانون الثاني.

### صفحة القائمة — استعلامان، بلا فلاتر

**لا فلترة جانبية ولا كود فلترة خلفها.** الكتالوج أقل من عشرين قطعة عند
الإطلاق؛ لوحة فلاتر فوق ثمانية عشر صنفًا أثاث، وأوجهها — اللون والمقاس — واحدة
تقريبًا في كل صف. ترتيب (الأحدث / الأكثر مبيعًا / السعر) وحقل بحث واحد. حين
يتجاوز الكتالوج ما يُقرأ بنظرة تُضاف الفلترة، وتُضاف حينها بمعرفة أي وجه طلبه
الناس فعلًا.

الصفحة **استعلامان لا أكثر**: واحد للمنتجات وواحد لكل متغيّراتها، ثم يُجمَّع
اللون في PHP. سؤال القاعدة عن ألوان منتج داخل حلقة العرض هو الطريقة التي تصير
بها صفحة سريعة بثلاثة منتجات غير قابلة للاستعمال بثلاثين — ولا يظهر ذلك في
المخرجات حتى يقع.

لا `LIMIT` ولا `OFFSET`: التقسيم يكلّف عبارة ثانية (‏`COUNT`، أو
‏`SQL_CALC_FOUND_ROWS` المهجورة ورحلتها) مقابل لا شيء عند هذا الحجم. حين يكبر
الكتالوج يعودان معًا وتصير الميزانية ثلاثة، عن قصد.

**بطاقة «صمّمه بنفسك» في الموضع الثالث** لا الأول: من لم يرَ بعد كيف تطبع الورشة
لا سبب عنده ليأتمنها على تصميمه. مثالان أولًا، ثم الدعوة. وهي البطاقة الملوّنة
الوحيدة في الشبكة، فتُلتقط بالعين بلا لافتة.

الشبكة **أربعة أعمدة على سطح المكتب واثنان على الجوال**، مصرّحة لا مستنتجة:
‏`auto-fill` يعطي ثلاثة أو خمسة حسب النافذة، وبطاقة تقع في مكان مختلف عند كل عرض
هي بطاقة لا يتعلّم أحد أين يبحث عنها.

الصور `loading="lazy"` بأبعاد صريحة و`srcset` لثلاثة مقاسات
(‏٤٠٠/٨٠٠/١٢٠٠). `tools/make-images.php` يولّدها، و`Image::responsive()` يعرف
التسمية فلا يعرفها أي قالب — ويعود إلى الأصل حين تغيب المشتقّات، لأن صفحة لا
تعرض شيئًا لأن أداة لم تُشغّل أسوأ من صورة أكبر من اللازم.

### صفحة المنتج

تبويبان فوق زر الإضافة مباشرة: **التصميم الجاهز** (شبكة مصغّرات، الاختيار يحدّث
الصورة والسعر فورًا) و**صمّم هذا التيشيرت** (يفتح الجزيرة، وتُحمَّل عند الضغط
لا قبله).

**السعر يتحدّث في الخادم.** كل تغيير للون أو المقاس أو التصميم أو الكمية يسأل
‏`/api/price.php`، وهو يمرّ على `PricingService` نفسها التي تمرّ عليها السلة وكاتب
الطلب. الثمن طلب واحد لكل تغيير — استعلام على صف مفهرس — والمقابل رقم صحيح لا
ينزلق عمّا سيُحصَّل.

**جدول المقاسات بالسنتيمتر**، مقيسًا على القطعة مسطّحة. أكثر أسباب الإرجاع مقاس
خُمِّن من حرف يعني شيئًا مختلفًا في كل متجر.

**وسوم Open Graph وبيانات schema.org** مبنية من الصفوف نفسها التي تعرضها الصفحة،
فلا تنزلق عمّا يراه الزائر. روابط المنتجات تُشارَك عبر واتساب — وهي قناة البيع
الأولى لا خاطرة لاحقة — فالصورة مطلقة العنوان ومطلوب أن تكون قابلة للجلب فعلًا،
وهو ما يفحصه القسم ٦.

### مسار الرفع المباشر

`upload.php`: ملف، وشبكة كميات، وملاحظة. لا محرّر ولا حساب.

هؤلاء أعلى طلبات المتجر قيمة وأقلّها صبرًا: من عنده ملف جاهز للطباعة وأربعون
قميصًا لا يريد أن يُمشى به في مشهد ثلاثي الأبعاد ليضع تصميمًا وضعه أصلًا.

**شبكة الكميات** لا صندوق كمية واحد: طلب فريق عشرة قمصان بخمسة مقاسات، وسؤاله
مقاسًا في كل مرة يعني خمس دورات في النموذج أو مكالمة هاتفية.

ما يخرج **صف `custom_designs` لا يُميَّز في بنيته عمّا يكتبه المحرّر**: نفس
الجدول، ونفس الأعمدة، و`design_json` مُصطنَع بشكل المحرّر نفسه — أوجه وكائنات
وأبعاد طبيعية ومعروضة — فتحكم عليه **`inspectState()` نفسها**. لا شيء لاحقًا
يستطيع التفريق بينهما لأنه لا يوجد ما يفرّق به: `source` وحده، وهو للسجل لا
للتفرّع. يفحص القسم ٤ ذلك بمقارنة مجموعتي الأعمدة المملوءة، لا بتشابه عام.

‏PDF يُقرأ `MediaBox` من الملف نفسه — لا Imagick ولا Ghostscript على استضافة
مشتركة — والنقاط ٧٢ منها بوصة. الملفات الشعاعية لا دقّة فيها لتسقط عليها،
فتُوصف بلا `naturalWidth` وتصل `inspectState()` إلى الحكم الذي تصل إليه لتصميم
محرّر فيه نصّ فقط: لا شيء نقطي ليُحكم عليه.

### السلة والدفع

**السلة صفوف لا جلسة.** جلسة PHP على استضافة مشتركة ملف يُكنس بعمر لا يتحكّم به
أحد، ولا يمكن دمجها بحساب لأنه لا يوجد ما يُدمج. رمز في كوكي يشير إلى صف يعيش
أطول من الجلسة، ويُسلَّم لحساب العميل لحظة تسجيل الدخول — فمن ملأ سلته ثم تذكّر
أن له حسابًا لا يجدها فارغة على الجانب الآخر من نموذج الدخول.

**الأسعار تُقرأ من القاعدة عند كل عرض وعند إنشاء الطلب.** السطر يخزّن معرّفات
وكمية ولا شيء غيرها — لا سعرًا ولا اسمًا ولا لونًا. من يعدّل سعرًا في أدوات
المتصفح يعدّل رقمًا على وشك أن يُرمى، وكذلك رسم التخصيص وخصم الكمية: كلاهما
يُحسب من `config/shop.php` والقاعدة، ولا يُقبل من الطلب أبدًا.

خصم الكمية **على السطر لا على الطلب**، لأن التوفير حقيقي على السطر: عشرة قمصان
متطابقة طبعة واحدة وسحبة واحدة من رفّ واحد. عشرة مختلفة عشرة من كلٍّ.

الدفع خلف `PaymentDriverInterface`. المنفَّذ الآن `CashOnDeliveryDriver` وحده —
الدفع عند الاستلام هو الغالب محليًا — لكن الإتمام يمرّ بالواجهة أصلًا، وهو الفرق
بين إضافة بوابة لاحقًا وإعادة كتابة الإتمام لاحقًا.

**الإتمام كضيف يعمل من البداية إلى النهاية.** الحساب اختياري ويُعرض بعد البيع لا
قبله.

**«المنتج المخصّص غير قابل للإرجاع» بجوار زر الإتمام**، لا في الفوتر: هذه آخر
لحظة يستطيع فيها العميل تغيير رأيه بقميص لا يُباع لأحد غيره، ودفن التنبيه حيث لا
يُقرأ هو السطر الأول من نقاش استرجاع.

وفوقه **ملخّص بصري لكل سطر مخصّص بصورة المعاينة المحفوظة** — نفس الصورة التي
ستعمل منها أرضية الإنتاج. وثيقة اتفاق تسبق الخلاف.

### قفل المخزون

إنشاء الطلب يكتب الرأس والسطور وينقص المخزون في **معاملة واحدة**، وصفوف
المتغيّرات مقفولة بـ `SELECT ... FOR UPDATE` طوالها. بلا القفل يقرأ عميلان
وصلا الإتمام في الثانية نفسها `stock = 1`، ويمرّان كلاهما، ويُقال لكليهما إنه
اشترى آخر قطعة. الصفوف مقفولة **بترتيب المعرّف** لأن معاملتين تأخذان الصفوف
نفسها بترتيبين مختلفين هي تعريف الجمود.

يفحص القسم ٣ ذلك على مستويين: بوصلتين متزامنتين على القاعدة مباشرة (الثانية
يجب أن تُحجَب)، ثم بطلبين حقيقيين عبر الإتمام (واحد يمرّ، والرفّ يبقى صفرًا لا
سالبًا).

### الطلبات ولوحة الإدارة

**رقم قابل للنطق** — `TS-4X7K2` — من أبجدية بلا `I` ولا `O` ولا `0` ولا `1`،
فلا حرف فيه ملتبس حين يُكتب بخط اليد على صندوق أو يُملى في خط سيّئ. والمعرّف
التسلسلي يقول لمنافس كم طلبًا وصل الشهر الماضي، ويقول لغريب إن تجربة ١٠٤٢ قد
تنجح.

**التتبّع بلا حساب**: رقم الطلب ورقم الهاتف. رقم خاطئ، ورقم صحيح بهاتف خاطئ،
وطلب لم يوجد قط — كلها تعطي **الجملة نفسها والحالة نفسها**. الفرق بين هذين
الجوابين هو بالضبط ما يخبر من يمشي في فضاء الأرقام أنه وجد واحدًا حقيقيًا.
والمقارنة تحدث في `WHERE` لا في فرع PHP، فلا يوجد تفرّع يمكن أن يُسرّب.
وفوقها تحديد معدّل: عشر محاولات لكل عشر دقائق تجعل البحث أطول من عمر المتجر.

الحالات `pending → paid → in_production → shipped → delivered` مع `cancelled`
و`refunded`، والانتقالات مُصرّحة في `OrderService::TRANSITIONS` — لا يُنقل طلب
من «ملغى» إلى «مشحون». **الإلغاء يعيد القطع إلى الرفّ**، والاسترجاع لا يفعل:
استرجاع بعد الشحن لا يعني أن القمصان عادت.

**ملف واحد لكل تصميم لا لكل قطعة.** فريق يطلب عشرة قمصان بخمسة مقاسات يرسل ورقة
واحدة إلى المكبس؛ ورقة لا تتغيّر لأن القميص تحتها XL. `print_files` مفهرس على
التصميم، فطلب العشرة يُنتج وظيفة واحدة وملفًا واحدًا — ولا يجد المشغّل خمسة
‏PDF متطابقة وخمس فرص لاختيار الخطأ منها.

**تصدير أوامر الإنتاج** (`/admin/export.php`) يعطي مضغوطًا فيه ملفات الطباعة
وورقة تجميع `collation.csv`: سطر لكل قطعة بالمقاس واللون والكمية والموضع، وعمود
يشير إلى ملف الطباعة. الورقة هي المهمّة — الـ PDF يقول ماذا يُطبع، والورقة وحدها
تقول على أي شيء وكم. وفيها BOM: بدونه يقرأ Excel ملف UTF-8 بترميز النظام
فتتحوّل كل أسماء الألوان العربية إلى طلاسم، على ورقة كل عملها أن تقول أي قميص
يُلتقط.

**البريد عبر SMTP بـ PHPMailer، لا `mail()`.** الأخيرة تسلّم الرسالة لثنائي محلي
بمُرسِل ظرفي لا سبب عند الطرف المستقبِل ليثق به، فتُصنَّف مهملات أو تُسقَط بلا
ارتداد — ويكتشف المتجر ذلك حين يتصل عميل ليسأل إن كان طلبه وصل. رسالتان فقط:
تأكيد الطلب، والشحن. رسالة عند كل تغيير حالة داخلي تدرّب الناس على تجاهل الرسائل.
الإرسال لا يوقف عميلًا أبدًا: فشله يُسجَّل والطلب يبقى، لأن بريد تأكيد تعذّر
إرساله ليس سببًا لرفض طلب حُجز مخزونه بالفعل.

### إصدارة الأصول

`.htaccess` يطلب من المتصفحات الاحتفاظ بـ CSS و JS أسبوعًا — وهو ما يجعل الزيارة
الثانية سريعة، وما يترك زائرًا عائدًا على ورقة أنماط الأسبوع الماضي بعد النشر.
الثابت `ASSETS` في `src/bootstrap.php` يُلحق بكل رابط أصل؛ ارفعه عند كل إصدار.

### الفحص

```bash
php -S 127.0.0.1:8899 -t public tools/router.php
php tools/verify-store.php          # معايير المتجر الاثنا عشر
```

٦٢ فحصًا تمرّ على المسارات الحقيقية — بكوكيز وجلسات ورموز CSRF ورفع ملفات
حقيقي عبر `CURLFile`، لأن أكثر هذه المعايير عن سلوك المتجر أمام مستخدم معادٍ أو
سيّئ الحظ، وخدمة تُستدعى من سكربت ليست أيًّا منهما.

## الأمن

- **CSRF**: `random_bytes(32)` في الجلسة، ومقارنة `hash_equals` في كل POST.
- **الجلسة**: `httponly` + `samesite=Lax` + `secure` على HTTPS، و
  `session_regenerate_id(true)` عند الدخول.
- **الرفع**: النوع من `finfo_file` لا من الامتداد ولا من `$_FILES['type']`،
  والاسم مُولَّد بـ `random_bytes(16)`، وحدّ ١٥ ميغابايت، و `.htaccess` يمنع
  تنفيذ PHP في `uploads`.
- **SVG**: يُفكّ بـ `DOMDocument` مع `LIBXML_NONET` وبلا `LIBXML_NOENT` (الذي
  يُعيد تفعيل استبدال الكيانات)، فتُحذف `<script>` و `foreignObject` وكل معالج
  `on*` وكل `href` خارجي. النسخة المعقّمة وحدها تُنشر، والأصل يُحفظ في
  `storage/originals/` خارج جذر الويب ولا يُقدَّم أبدًا.
- **الإخراج**: `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')` لكل نص، والبيانات
  إلى JavaScript داخل `<script type="application/json">` مع `JSON_HEX_TAG`
  وأخواته. لا قيمة تُطبع داخل كود JS.
- **الأسعار** تُقرأ من الكتالوج عند إنشاء الطلب لا من السلة، فسعر مُرسَل من
  العميل يُتجاهَل.
- **تحديد المعدّل** على الرفع وإنشاء الطلبات والدخول، بملفات مقفولة بـ `flock`
  فتعمل عبر عمليات PHP متعدّدة.
- كل استعلام مُجهَّز، بلا استثناء.
